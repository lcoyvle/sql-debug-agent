# 从 V0 到 SFT 与 GRPO

## V0：先验证 Agent 闭环（已完成）

目标是证明执行器、验证器、反馈、修正和评测能够连通。规则修复器只承担离线占位作用，不把演示集的 100% 当成模型效果。

完成标准：

- 所有写 SQL 都会被拒绝。
- 执行错误和语义错误能够分开统计。
- 每轮 SQL、反馈和奖励都可追踪。
- 单元测试可以稳定复现。

## V1：本地真实模型基线（已完成）

当前结果：

- 模型：`qwen2.5-coder:1.5b-instruct`，通过本地 Ollama 运行。
- 独立测试集：30 题，与规则演示集和训练数据分离。
- 修复成功：16/30，准确率 53.3%。
- JOIN：0/5；日期：2/5；过滤：2/5，是主要短板。
- 详细轨迹保存在 `artifacts/baseline_report.json`。
- 自动分析保存在 `artifacts/badcase_analysis.md`。

这份结果作为后续优化基线，不使用规则模式的 100%。

## V2：构建真正的数据集（已完成第一版）

从业务目标倒推数据，而不是只下载公开数据：模型需要修复金融分析 SQL，因此应重点覆盖容易造成错误报表的类型。

已构建 200 条：

| 错误类型 | 数量 | 构造方式 |
|---|---:|---|
| JOIN | 60 | 按 0/5 的最大短板加权；覆盖内外连接、连接键、NOT EXISTS |
| Aggregation | 30 | GROUP BY、聚合粒度、聚合函数 |
| Duplicate Counting | 15 | JOIN 后客户重复计数、COUNT DISTINCT |
| Filter | 35 | 状态、金额、地区和条件遗漏 |
| Date | 30 | 月份、日期边界、分组粒度 |
| Schema Linking | 20 | 字段名、表归属与近似字段 |
| Syntax Error | 10 | 基线已 5/5，因此只做巩固 |

数据处理流程：

1. 写出自然语言问题和正确 SQL。
2. 执行正确 SQL，保存标准结果。
3. 按错误模板注入一个可解释错误。
4. 执行错误 SQL，记录数据库反馈和结果差异。
5. 去重，并按数据库或问题模板分组切分，避免训练集泄漏到测试集。
6. 按 `template_id` 分组切分，避免同模板同时进入训练和内部评测。
7. 对 30 题独立测试集做精确指纹防泄漏检查。

当前产物为 158 条训练数据、42 条按错误类型分层且模板隔离的内部评测数据。自动验证已确认
200 条参考 SQL 均可执行、错误 SQL 均不能匹配参考结果、样本指纹无重复、与
独立测试集无精确重合。训练前仍建议人工抽检至少 20 条。

## V3：SFT（第一轮已完成）

根据 V1 的失败类型扩充数据，再接入 0.5B～1.5B 代码小模型并记录未训练指标。之后使用 LoRA 做 SFT，训练目标为：

```text
问题 + Schema + 错误 SQL + 执行反馈 → 修正 SQL
```

至少比较：

- Base 模型一次修复。
- SFT 模型一次修复。
- SFT 模型最多三轮修复。
- 按错误类型拆分的准确率。

第一轮实验使用 M1 8GB MacBook Air、MLX-LM、Qwen2.5-Coder-1.5B 4-bit：

- 5 步 smoke test 成功，Adapter 能被 Agent 加载并修复 SQL。
- 正式训练 50 步，验证损失从 0.507 降到 0.026，峰值内存 1.831GB。
- 同条件 MLX Base：24/30（80.0%）。
- SFT V1：25/30（83.3%），净提升 1 题（+3.3 个百分点）。
- 修复 2 个 Base 失败案例，但新增 1 个过滤条件回退案例。

训练过程中发现模型在正确 SQL 后重复输出 `!`。Agent 增加了流式首行停止协议，
将生成格式和数据库执行协议对齐；该问题作为输出终止 Bad Case 保留在实验报告中。

## V4：Bad Case 分析（SFT V1/V2 已完成）

不要看完总体准确率就直接做 RL。输出一份自动报告，至少包含：

- 每类错误的样本数和成功率。
- 可执行但结果错误的比例。
- 重复生成相同 SQL 的比例。
- 每个任务平均修正轮数。
- 修正后引入新错误的比例。

优先继续补 SFT 数据；只有当数据清洗、类别补齐和至少两轮 SFT 迭代都不再明显改善时，再考虑 RL。

SFT V1 剩余 5 个失败：聚合计数、日期边界、过滤值、零金额客户 JOIN、日期字段
链接各 1 个。下一步构建 SFT V2 的困难样本和对照样本，尤其补充 `COUNT(t.id)`、
ON/WHERE 条件位置、精确日期值以及防止已学会过滤能力回退的数据。

SFT V2 已增加 60 条针对性样本并完成 50 步训练，但结果否定了原假设：

- 原 30 题已参与 V1 Bad Case 分析，因此重新定义为开发集；V2 为 22/30（73.3%），
  低于 V1 的 25/30（83.3%）。
- V2 数据构建前冻结的新 35 题留出集上，Base 27/35（77.1%）、V1 26/35
  （74.3%）、V2 23/35（65.7%）。
- 验证损失从 0.791 降至 0.032，却没有带来任务级泛化，说明只看 loss 会误判。
- 典型回退为 SQLite 方言错误、凭空增加过滤条件和 `LEFT JOIN` 条件位置错误。

因此当前最优仍是 Base。下一轮先做 SFT 数据质量和泛化优化，不把已经看过的 35 道
留出题直接加入训练；未来验证还需要再生成一份新的冻结留出集。

### SFT V3 泛化实验（已完成）

- 冻结第二套 28 题最终留出集，每类 4 题。
- 使用 158 条 V1 回放数据和 60 条多模板增量数据，不沿用 V2 增量。
- 训练 10/20/30 步候选，用开发集选择 30 步版本。
- 修复 execution-match 把等价 SQL 因列别名不同判错的问题。
- 最终 Base 18/28（64.3%），V3-30 19/28（67.9%），提升 1 题。
- JOIN 25% → 50%，重复计数 0% → 25%，但 Schema Linking 回退 1 题。

V3 证明数据策略出现正向信号，但尚未达到稳定泛化标准。

## V5：决定是否需要 GRPO（已完成）

V1/V2 当时的自动阶段门槛结果是 **不进入 RL**。三个条件全部未通过：最优 SFT 未超过 Base、
仍有回退案例、第二轮 SFT 低于第一轮。可用
`python -m sql_debug_agent summarize-experiment` 重建该结论。

V3 阶段，SFT 已在新留出集超过同提示词 Base，但仍有 1 个回退案例，因此当时仍不进入
RL。下一次门槛重点是消除回退，并确认多轮错误主要来自不会利用执行反馈，而不是单轮
SQL 基础能力不足。

### RL V1 前置层（已完成，未启动训练）

- 从 30 道开发题和 60 条 V3 增量题构建 90 条 GRPO prompts。
- 每题构造重复提交、空结果捷径、危险写操作三类负例，共 270 对偏好数据。
- 奖励同时在两套同 Schema、不同数据分布的数据库上验证，防止偶然结果匹配。
- 加入执行奖励、答案奖励、修复奖励、重复惩罚、终局失败惩罚和安全惩罚。
- 21 项测试覆盖单数据库碰巧相等、空结果、列别名和危险 SQL 等情况。
- 正确答案与负例的最小奖励间隔为 1.50。

该阶段的 `training_ready=false`。随后先对剩余错误做 SFT/偏好优化，只有无回退且多轮反馈
确实是主要瓶颈时，再正式运行 GRPO。

### RL V1 真实 Rollout 回放（已完成）

- V3-30 对 90 条 prompts 生成真实候选，未更新参数。
- 安全率 100%，双库可执行率 98.9%，双库正确率 71.1%。
- 84 条相对初始错误奖励改善，6 条持平；6 条重复提交原 SQL。
- 奖励分布为四档，标准差 0.71，具备候选排序信号。
- 3 条候选触发跨数据库结果分歧，证明单数据库奖励存在真实误判风险。
- 26 条失败 rollout 已转换成真实 hard preference pairs。
- 主要短板：重复计数 0/7，JOIN 8/15，日期 10/15。

当时奖励层门槛已经通过，但模型层门槛仍未通过，因此优先用真实 hard pairs 做受控偏好
优化，并继续监控 Schema、Filter、Syntax 等强项是否回退。

### Corrective Replay 偏好替代实验（已完成，候选被拒绝）

- MLX-LM 0.31.3 没有 DPO/GRPO trainer，因此先运行明确标注的 corrective replay SFT。
- 26 条真实失败纠错与 26 条强项保护组成 52 条训练数据。
- 从 V3-30 Adapter 以 5e-6 学习率继续训练 5 步和 10 步。
- V3-30、5 步候选、10 步候选的开发集均为 21/30。
- 10 步候选的 90 条双库回放仍为 64/90，重复提交仍为 6 条。
- 没有新修复，也没有回退；自动门槛拒绝候选，保留 V3-30。

结论：普通 SFT 只学习 chosen token，不能利用 chosen/rejected 的相对偏好信号。下一步
若要完成真正的偏好优化或 GRPO，应准备带 pairwise/group-relative loss 的云端 GPU
训练包；如果保持纯本地，则继续做 Agent 策略优化，但不能将其描述为 GRPO。

### 云端 SFT 与 GRPO（已完成）

- 使用标准 Hugging Face `Qwen/Qwen2.5-Coder-1.5B-Instruct`，避免把 MLX Adapter
  错当成可被 PyTorch/TRL 直接加载的 PEFT Adapter。
- 先用 218 条 V3 训练数据和 42 条内部验证数据重建标准 QLoRA SFT Adapter。
- 第一版 2-generation smoke test 的 `reward_std` 始终为 0，因此没有盲目扩展训练。
- V2 改用 26 条真实失败难例、4 generations、temperature 1.2；奖励同时执行两套
  SQLite 数据库。
- 免费 T4 配置使用 4-bit NF4、LoRA、梯度检查点；60 步 SFT 和 40 步 GRPO 均完成。
- 40 步中有 3 步产生非零奖励方差，证明存在真实但稀疏的 GRPO 学习信号。
- 最终 holdout 不进入云端训练包，避免训练与模型选择泄漏。

执行入口为 `cloud_grpo/prepare_bundle.py`，零基础说明为
`cloud_grpo/README_COLAB.md`。最终 GRPO Adapter 已保存并通过冻结测试集验证。

适合引入 RL 的信号：

- SFT 已经会生成合法 SQL，但不会根据执行反馈继续尝试。
- 模型经常重复同一个错误。
- 单轮正确率尚可，多轮成功率没有提高。
- 结果正确与否可以通过数据库稳定自动验证。

第一版奖励建议：

```text
安全且可执行                         +0.2
执行结果与参考答案一致               +1.0
首次错误后成功修复                   +0.3
重复提交相同 SQL                     -0.2
触发写操作或越权行为                 -1.0
超过最大轮数仍未成功                 -0.2
```

奖励函数必须在训练前用固定样例做单元测试，防止模型通过空结果、删减列或其他捷径骗取奖励。

## V6：最终对比验证（已完成）

固定同一份隔离测试集，对比 Base、SFT、SFT+GRPO。除了总体正确率，还要报告安全性、各类 Bad Case、工具调用次数和失败案例。只有 SFT+GRPO 在未见测试集上稳定提升，才能说明强化学习环节有效。

最终 28 题、双数据库、确定性单轮修复结果：

| 模型 | 正确数 | 正确率 |
| --- | ---: | ---: |
| Base | 16/28 | 57.1% |
| SFT | 23/28 | 82.1% |
| SFT + GRPO | **25/28** | **89.3%** |

GRPO 相对 SFT 修复 2 题、回退 0 题，通过本项目的最终接受标准。完整结论与局限见
`docs/final_report.md`。

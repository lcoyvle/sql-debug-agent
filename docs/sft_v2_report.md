# SFT V2：针对性增量数据、回退与阶段决策

## 实验问题

SFT V1 在原 30 题上由 80.0% 提升到 83.3%，但仍有 5 个失败案例。V2 的假设是：
补充这些失败背后的通用模式，并加入明确的 SQL 终止符，可以继续提高修复正确率。

因为原 30 题已经参与 V1 Bad Case 分析，它从本轮开始被重新定义为**开发集**。在生成
V2 数据之前，项目另外冻结了 35 道最终留出题；这些题不进入训练，也不用于选择 V2
数据模板。

## 数据优化

V2 在 V1 的 158 条训练样本上增加 60 条 SQLite 验证通过的针对性样本，每类 12 条：

- 聚合：`LEFT JOIN` 后用 `COUNT(t.id)`，避免 `COUNT(*)` 把空记录计为 1。
- 日期：精确保留问题给出的日期边界。
- 过滤：风险等级与地区值的对照样本。
- JOIN：把条件放入 `CASE` 或 `ON`，避免 `WHERE` 破坏零记录对象。
- Schema Linking：在谓词中使用真实字段。

V2 训练集共 218 条，内部验证集沿用 V1 的 42 条模板隔离数据。生成脚本同时检查与
开发集、V1 原始数据和最终留出集没有精确指纹重合。

## 训练配置

- 模型：`mlx-community/Qwen2.5-Coder-1.5B-Instruct-4bit`
- 方法：MLX-LM 4-bit LoRA，训练最后 4 层
- 训练步数：50
- Batch size：1，梯度累积：4
- 学习率：`1e-5`
- 峰值内存：1.927 GB
- 验证损失：0.791 → 0.032

## 结果

### 原 30 题开发集

| 模型 | 正确题数 | 准确率 |
| --- | ---: | ---: |
| SFT V1 | 25/30 | 83.3% |
| SFT V2 | 22/30 | 73.3% |

V2 没有修复新的开发题，反而让 3 题回退。低验证损失没有转化为真实任务收益。

### 冻结的 35 题最终留出集

| 模型 | 正确题数 | 准确率 |
| --- | ---: | ---: |
| MLX Base | 27/35 | 77.1% |
| SFT V1 | 26/35 | 74.3% |
| SFT V2 | 23/35 | 65.7% |

分类上，V1 把 JOIN 从 20% 提升到 60%、聚合从 80% 提升到 100%，但过滤从 80%
降到 20%。V2 保持聚合与重复计数能力，却把日期降到 20%，JOIN 也回到 20%。

## Bad Case 分析

典型失败不是 SQL 不能执行，而是模型做了不受问题支持的改写：

- 把 SQLite 日期比较改成不支持的 `TO_DATE(...)`。
- 在修复风险值时擅自增加 `account_type` 条件。
- 需要保留零记录对象时，虽然生成 `LEFT JOIN`，却仍把右表条件留在 `WHERE`。
- 面对已经接近正确的 SQL，有时直接重复原 SQL，没有完成最小必要修改。

这说明 V2 的问题不是“训练不够久”，而是小数据上的模板记忆和能力遗忘。继续增加步数
很可能让验证损失更低、泛化更差。

## 阶段决策

暂不进入 RL。项目设置三个门槛：最优 SFT 必须超过 Base、不能出现任务回退、第二轮
SFT 不能低于第一轮。本轮三个门槛均未通过。

下一轮应优先：

1. 加入“只做最小必要修改”的正反对照样本。
2. 明确 SQLite 方言，不允许生成 `TO_DATE` 等其他数据库函数。
3. 使用类别均衡采样和 V1/Base 能力回放，减轻灾难性遗忘。
4. 用新的模板隔离验证集选择 checkpoint，而不是只看 token-level loss。
5. 下一次最终结论必须使用另一份从未看过的新留出集，不能把当前 35 题回填训练。

`artifacts/sft_final_summary.md`。

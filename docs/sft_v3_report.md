# SFT V3：泛化数据、候选选型与执行等价评测

## 目标

V1/V2 表明低训练损失不能保证真实任务提升。V3 不继续堆叠 V2 的窄模板，而是验证三个
更明确的假设：

1. “只做最小必要修改”可以减少擅自添加过滤条件。
2. 明确 SQLite 方言可以减少 `TO_DATE` 等不可执行写法。
3. V1 数据回放配合多模板增量数据，可以缓解能力遗忘。

## 数据与隔离

- V1 回放数据：158 条。
- V3 新增数据：60 条，覆盖七类错误。
- V3 训练集：218 条；内部验证集：42 条。
- 新最终留出集：28 条，每类 4 条，在 V3 数据生成和训练前冻结。
- 与原 30 题开发集、旧 35 题留出集、V1/V2 数据均无精确指纹重合。
- V2 的 60 条窄模板不进入 V3，用于检验替换数据策略而不是继续累加。

## 候选选择

预先训练 10、20、30 步三个候选，只在原 30 题开发集选型：

| 候选 | 验证损失 | 开发集正确率 |
| --- | ---: | ---: |
| V3-10 | 0.531 | 60.0% |
| V3-20 | 0.373 | 66.7% |
| V3-30 | 0.077 | 70.0% |

因此在查看新留出集之前固定选择 V3-30。训练峰值内存约 2.006 GB。

## 评测器修复

初次分析发现，旧验证器要求候选 SQL 的 SQLite 返回列标题与参考 SQL 完全一致。
这会把值完全相同、仅表达式或别名不同的 SQL 判错，例如：

- `substr(txn_date,1,7)` 与 `strftime('%Y-%m', txn_date)`。
- JOIN `ON` 条件与等价的 `CASE WHEN` 聚合。
- 有无不影响结果值的输出别名。

项目的核心指标是 execution-match，因此现在只比较有序结果值，不要求复制参考 SQL 的
列标题。列数和列顺序仍通过结果元组约束。相应单元测试已加入。修复后还发现一条
duplicate-counting 留出题的错误 SQL 与答案碰巧数值相同，因此按数据质量规则替换为
真正不同的 Bad Case，再重新运行两组最终评测。

## 最终结果

同一提示词、数据库、最大轮数和修正后的 execution-match 指标：

| 模型 | 正确题数 | 准确率 |
| --- | ---: | ---: |
| V3 Prompt Base | 18/28 | 64.3% |
| SFT V3-30 | 19/28 | 67.9% |
| 净变化 | +1 | +3.6 个百分点 |

分类变化：

- JOIN：25% → 50%。
- Duplicate Counting：0% → 25%。
- Schema Linking：100% → 75%。
- 其余类别持平。

V3 修复 `v3_holdout_duplicate_counting_01` 和 `v3_holdout_join_type_04`，但让
`v3_holdout_schema_linking_01` 回退。

## 阶段决策

V3 首次在新冻结留出集获得正向净提升，说明新的数据逻辑有价值；但提升只有 1 题，且
仍有回退，所以未通过“无回退”门槛。暂不进入 RL。

下一阶段不应继续盲目增加训练步数。优先修复两项：

1. 将 execution-match 奖励作为训练选型指标，而不是 token loss。
2. 针对重复计数、JOIN 否定语义和最小字段替换增加成对偏好数据；待 SFT 无回退后，
   再把“重复提交错误 SQL、不会利用执行反馈”作为 GRPO 的明确目标。

# RL V1 数据与稳健奖励设计

## 为什么先构建奖励、不直接训练

SFT V3 在新留出集由 64.3% 提升到 67.9%，但仍出现一个回退案例。此时直接运行
GRPO，无法判断收益究竟来自多轮决策，还是奖励函数放大了已有错误。因此本阶段只完成
RL 数据、奖励实现和防作弊测试，并把 `training_ready` 保持为 `false`。

## RL 要解决的问题

SFT 已经能稳定生成安全、可执行的 SQL，剩余问题集中在：

- 收到“结果不正确”的执行反馈后仍重复原 SQL。
- SQL 能执行，但 JOIN、重复计数或否定语义仍然错误。
- 为了得到看似合理的结果，擅自增加题目未要求的条件。
- 在单个小数据库上通过偶然的数据分布得到正确结果。

这些问题比基础语法更适合用可验证奖励优化，因为数据库能够提供自动、确定的执行反馈。

## 数据构建

数据来源只包括：

- 30 道开发题。
- 60 条 V3 多模板增量题。

`final_holdout.jsonl` 和 `final_holdout_v3.jsonl` 均被排除。每个问题生成一条不包含
参考答案的 GRPO prompt，并生成三种偏好负例：

1. `unchanged`：重复提交原错误 SQL。
2. `empty_result_shortcut`：外包一层 `WHERE 1=0`，尝试用空结果骗奖励。
3. `unsafe_write`：生成危险写操作。

最终得到 90 条 prompts 和 270 对 chosen/rejected 偏好数据。

## 奖励函数

| 行为 | 分值 |
| --- | ---: |
| 两套数据库均安全可执行 | +0.2 |
| 两套数据库结果均与参考一致 | +1.0 |
| 从上一轮错误成功修复 | +0.3 |
| 重复提交相同 SQL | -0.2 |
| 最后一轮仍失败 | -0.2 |
| 写操作或越权行为 | -1.0 |

答案奖励要求候选 SQL 在演示数据库和扩展训练数据库上都与参考 SQL 返回相同的有序值。
两套数据库 Schema 相同、数据分布不同，可以识别在单一小数据库上偶然等价的错误 SQL。

例如演示库中“华北客户数”和“西南客户数”碰巧都是 1，单数据库验证会误判为正确；
扩展数据库中的数量不同，多数据库奖励能够拒绝该捷径。

## 防作弊测试

测试覆盖：

- 危险 SQL 固定得到 -1.0，且不会执行。
- 空结果查询不能获得答案奖励。
- 删列或改变列顺序不能获得答案奖励。
- 单数据库偶然相等不能获得答案奖励。
- 只改变 SQL 列别名、结果值不变时不会被误罚。
- 所有偏好对必须满足 `chosen_reward > rejected_reward`。

当前 270 对数据的奖励间隔最小 1.50、平均 1.95、最大 2.50。

## 复现

```bash
.venv/bin/python -m sql_debug_agent build-rl-data
.venv/bin/python -m unittest discover -s tests -v
```

产物位于 `artifacts/rl_v1/`。后续只有在 SFT 消除回退，并确认剩余错误主要来自多轮
反馈利用不足时，才把 `training_ready` 改为 `true` 并接入正式 GRPO trainer。
